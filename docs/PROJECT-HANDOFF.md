## 1. What this is

The public marketing site for **Stonehaven Lending**, a mortgage **brokerage**
(never a direct lender), NMLS #1752355, based in Alpharetta, Georgia.

It is a static HTML site with no framework and no bundler. Pages are either
hand-written or generated by Python scripts from Python config files. It is
bilingual: English at the root, Spanish under `es/`.

Scale, as of this handoff:

| | Count |
|---|---|
| Tracked files | 296 |
| HTML pages | 175 |
| Sitemap entries | 120 |
| Python generators | 4 |
| Linters | 4, plus a Spanish casing gate |
| Test suites | 8, all passing |

Product lines: DSCR rental-property financing, HELOC and cash-out, residential
mortgages, commercial, SBA, and the newest line, Family Opportunity.

## 3. The single most important rule: most pages are generated

Editing a generated HTML file by hand is the most common way to break this
project. The next build overwrites the edit and the change silently disappears.

Before editing any `.html`, check whether a generator owns it.

| Generator | Reads | Writes |
|---|---|---|
| `scripts/build-family-lps.py` | `scripts/family_lp_config.py` | `family-home-financing.html`, `buy-a-home-for-parents.html`, `family-housing-options.html`, `request-received.html`, `js/family-config.js`, `netlify/functions/family-shared.json` |
| `scripts/build-dscr-personas.py` | `scripts/dscr_lp_config_a.py`, `dscr_lp_config_b.py` | the 17 pages in `dscr/`, **and it injects a section into `dscr.html` between markers** |
| `scripts/build-heloc-personas.py` | `scripts/heloc_personas_config.py` | the HELOC persona pages in `heloc/` |
| `scripts/build-heloc-ads.py` | `scripts/heloc_ads_config.py` | the HELOC ad landing pages in `heloc/` |
| `scripts/new-post.mjs` | a JSON brief | one blog post **plus its Spanish mirror**, and it edits both blog indexes, `_redirects` and `sitemap.xml` |

Two traps in that table. `dscr.html` is hand-written **except** for the block the
persona generator owns, so a hand edit inside those markers is lost on the next
build. And the two HELOC generators both write into `heloc/`, so a slug defined
in both configs would have one silently overwrite the other.

`scripts/credit_bands.py` is shared by several generators and holds the owner's
standard ten credit-score bands. Change it in one place and rebuild.

Rebuild commands:

```bash
python3 scripts/build-family-lps.py
python3 scripts/build-dscr-personas.py
python3 scripts/build-heloc-personas.py
python3 scripts/build-heloc-ads.py
```

## 4. Blog publishing

All blog content ships through `scripts/new-post.mjs`, which takes a JSON brief
and writes **both languages in one run**. A Spanish mirror is mandatory, not
optional. Ten posts means twenty pages plus twenty redirect and sitemap lines.

```bash
node scripts/new-post.mjs post.json
```

The brief shape is `{slug, date, en:{title,desc,eyebrow,body,terms}, es:{...}}`.

Two conventions that are easy to get wrong:

- **Author is always the Organization**, never a person. Naming a human author is
  gated on an owner fact that has not been supplied, and no article may be
  labelled as reviewed by anyone unless that review actually happened.
- **Blog posts carry one JSON-LD block, `BlogPosting`.** No `FAQPage` and no
  `BreadcrumbList`. Removing `FAQPage` sitewide was a deliberate decision after
  Google retired the feature. The older `dscr/` persona pages still carry it;
  that is legacy, do not copy it forward.

The blog index is titled **"Closings"** and its CTA disclaimer asserts the posts
are illustrative of transactions already closed. Ten educational DSCR guides now
sit under that framing. See section 8.

## 5. Testing and gates

Everything below passes as of 2026-09-12.

```bash
# math engines, 8 suites
for t in tests/*.test.mjs; do node --test "$t"; done

# content and compliance linters
node scripts/lint-family-lps.mjs
node scripts/lint-dscr-personas.mjs
node scripts/lint-heloc-personas.mjs
node scripts/lint-es-casing.mjs

# the release gate Netlify itself runs, exit 1 means clean
grep -rlE 'STONEHAVEN_OWNER_FACT_REQUIRED|555-0100|Call ,|call  to|Llame al ,|Llame al  |is a commercial real estate lender|prestamos de forma directa|[Gg]uaranteed approval|[Ll]owest rate|[Ee]veryone qualifies' --include='*.html' .
```

There is no single aggregate command. Run all of the above before pushing.

### Only one of these is actually automated

This is the most misleading thing about the project, so read it carefully.

**The grep in `netlify.toml` is the only automated gate.** It runs inside the
build, and a match fails the deploy outright. There is no warning mode and no
per-file exemption.

**The four linters are not gates. Nothing runs them.** There is no
`package.json` anywhere in the repository, and the single GitHub workflow,
`.github/workflows/site-monitor.yml`, is post-deploy synthetic monitoring that
never invokes a linter. Worse, the build command deletes `scripts` and `tests`
*before* the grep runs, so the linters could not execute during a build even if
something tried.

So the linters are a manual discipline that depends on someone remembering. They
are also stricter than the deploy gate: they catch percentages, APR mentions,
tax-deductibility claims, disability-related form fields and much else that the
grep does not.

Two consequences worth acting on:

- Running the linters before every push is not optional hygiene. It is the only
  time they run at all.
- **Wiring them into CI is the highest-value hardening available on this
  project.** A newcomer will reasonably assume they already block deploys.

The deploy grep is also case-sensitive in places. `[Gg]uaranteed approval` does
not catch `GUARANTEED APPROVAL`, and the direct-lender pattern is fully
case-sensitive, so a page shouting in capitals would pass a gate the linters
would fail.

### The rules those checks encode

Worth knowing before you write anything, because most are invisible until
something fails.

- **Brokerage, never lender.** Capital is always "arranged through" a third
  party. The deploy gate bans the direct-lender claim in English and Spanish.
- **No pricing outside `/blog`.** All three page linters ban any decimal
  percentage and the word APR. Inside `/blog`, rates are permitted as facts of a
  closed deal and every rate must carry its closing date. Residential rates must
  always be paired with an APR, because a bare rate is a Regulation Z trigger
  term.
- **The Family pages ban every percentage and dollar amount outright**, which is
  what keeps those consumer-purpose pages clear of Regulation Z trigger terms.
- **No tax advice.** The HELOC linter bans any `tax-deduct` wording. Note this
  rule exists only as that one regex: it is **not** written down as policy and
  **not** enforced on DSCR, blog or Family content. Treat it as a sitewide rule
  anyway.
- **No guarantees or superlatives.** No guaranteed approval, no lowest rate, no
  "everyone qualifies", no "approved in X days".
- **No em dashes sitewide.** Note a conflict: `docs/STYLE-es.md` permits en
  dashes for numeric ranges, but the Family linter bans en dashes outright on its
  four pages. On those pages the linter wins.
- **Spanish is sentence case**, addresses the reader as *usted*, and its legal
  disclosures are reviewed text that must not be edited in a copy pass.
- **Deal write-ups carry no names, addresses or parcel ids**, and loan amounts
  are rounded.
- **The disability page may not ask about income, benefits, capacity to work or
  anything medical.** The Family linter fails the build on those words appearing
  in its form.

Local preview:

```bash
python3 scripts/dev-server.py              # the main site
node scripts/family-dev-server.mjs 8902    # Family pages with a working endpoint
```

## 6. Security posture

A full review was completed 2026-09-11 and is written up in
`docs/security-review-2026-09-11.md`. Summary of what a newcomer must know:

**Response headers live in `_headers`, never in `netlify.toml`.** The build
command deletes `netlify.toml` while it runs, so header rules declared there are
silently dropped. This was a live bug: `/request-received` had been serving
neither its noindex nor its no-store. Verify any header change with
`curl -sI https://stonehavencre.com/`.

**There is an enforced Content-Security-Policy with an origin allowlist.** Adding
any new third-party script, font, iframe or beacon requires adding its origin to
`_headers` or it is blocked in production. To roll back fast, rename the key to
`Content-Security-Policy-Report-Only`.

**`netlify/functions/lead-capi.js` is public and now hardened**: same-site origin
required, per-IP rate limit, known event names only, payload allowlist. Its rate
limit is in-memory per function instance, so it slows abuse rather than stopping
it.

Audited and found clean, so do not re-audit without reason: no committed secrets,
no client-side XSS, no open redirects, no tabnabbing, and `_redirects` has no
proxy or splat-interpolation rules.

## 7. CRM integration, and why it is blocked

Website leads do **not** currently reach the CRM. They land in the Netlify Forms
inbox under the shared `lead` form, and somebody has to watch it.

Setting `FAMILY_CRM_INTAKE_URL` to the CRM's `/api/intake/website` **will not
work in production as both sides are written**. Two independent reasons, both in
`app/api/intake/website/route.ts`, re-verified 2026-09-12:

1. In production the route requires `requestOrigin === allowedOrigin`, with an
   explicit "no origin-less bypass in prod" comment. The Netlify Function is a
   server-to-server `fetch` and sends no `Origin` header. Result: 403.
2. A CAPTCHA secret is mandatory in production, and the function posts
   `token: ""`. Verification fails. Result: 400.

The route is built for browser form posts, not server-to-server calls. The fix
is to add a shared-secret path to the CRM route that satisfies both gates, then
set that secret on both sides.

**Page ids.** The CRM validates an allowlist in
`lib/intake/connectors/website.ts`. It now includes `family-overview`,
`family-parents` and `family-adult-child`. These ids are `data-sh-form` values,
not URL paths. The commits sit on `feat/residential-product-website-intake` and
are **not merged to `main`**, so the CRM will reject these ids until they are.

## 9. Service area: what may and may not be claimed

This is a licensing matter, not a marketing preference.

**Residential is licensed in six states**, and the licensing line names each:

> Residential mortgage programs are offered in Georgia (Residential Mortgage
> Licensee #19721 · MLO #169068), Alabama (#22874), Tennessee (#165060), Florida
> (#MBR3925), North Carolina (#B-198926), and South Carolina.

**Business-purpose DSCR and commercial financing is described as arranged
nationwide**, with availability varying by state.

**Do not write state-specific DSCR availability claims.** The approved-lender
state matrix is recorded as an unverified fact in the internal claims register.
"Nationwide, availability varies by state" is the permitted phrasing.

## 11. Things that will bite you

- **Editing generated HTML.** Section 3. Check for a generator first.
- **Adding headers to `netlify.toml`.** They are silently discarded. Use
  `_headers`.
- **Adding a third-party script without updating the CSP.** It is blocked in
  production with no obvious error.
- **Pushing to `main`.** That is a production deploy. There is no staging.
- **Em dashes.** Banned throughout. The Family generator raises on them and the
  linters check for them.
- **Publishing an English post without its Spanish mirror.** The generator writes
  both; do not defeat it.
- **Adding `funnel.js` or `site-config.js` to a Family page.** Those files
  unconditionally initialise the Meta Pixel, which is exactly what those pages
  must not do. The linter checks for it.
- **The build deletes `docs`, `tests`, `scripts`, `downloads` and
  `netlify.toml`.** Anything that must be served cannot live there.
- **Rates outside `/blog`.** The standing rule is no pricing anywhere except
  closed-deal write-ups, where every rate carries its closing date.
